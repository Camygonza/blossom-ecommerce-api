# Decisiones (ADR corto)

Plantilla: **Contexto** · **Decisión** · **Alternativa descartada** · **Consecuencia**.

## D1 — Dos repos (api / web)
- Contexto: la prueba pide backend y frontend.
- Decisión: dos repos independientes; `docker-compose` del api levanta todo.
- Descartada: monorepo.
- Consecuencia: despliegue y CI separados; contrato por OpenAPI.

## D2 — Herencia JOINED para Product
- Contexto: la prueba exige herencia; hay productos físicos y digitales.
- Decisión: `Product` abstracta + `PhysicalProduct` / `DigitalProduct`, estrategia JOINED.
- Descartada: SINGLE_TABLE (columnas nulas), TABLE_PER_CLASS (uniones costosas).
- Consecuencia: esquema normalizado a cambio de un JOIN por consulta.

## D3 — OrderItem en vez de @ManyToMany
- Contexto: Order N↔N Product con cantidad y precio histórico.
- Decisión: entidad `OrderItem` con `quantity` y `unitPrice` congelado.
- Descartada: `@ManyToMany` directo (no admite atributos).
- Consecuencia: el historial no cambia si el precio cambia.

## D4 — JWT stateless con refresh
- Contexto: API segura y escalable sin sesión.
- Decisión: access token corto + refresh token; BCrypt; roles.
- Descartada: sesión en servidor.
- Consecuencia: la revocación inmediata exige lista de bloqueo (roadmap).

## D5 — RTK Query con axios
- Contexto: estado global y llamadas HTTP.
- Decisión: Redux Toolkit + RTK Query con `baseQuery` sobre axios (interceptor JWT).
- Descartada: Context + fetch manual.
- Consecuencia: caché, invalidación y estados de carga sin boilerplate.

## D6 — Versiones actuales: Spring Boot 4.0.8 y React 19
- Contexto: Spring Initializr ya no ofrece Boot 3.x; el template de Vite trae React 19.
- Decisión: Boot 4.0.8 (línea estable más madura) con Java 21 LTS; React 19, MUI 9, Vite 8, TS 6.
- Descartada: forzar Boot 3.x / React 18 (versiones en fin de soporte).
- Consecuencia: Spring Security 7 y Jackson 3; verificar compatibilidad de librerías (springdoc 3.1.1, jjwt 0.13.0, MapStruct 1.6.3).

## D8 — IDs Long IDENTITY y paquete raíz com.blossom.ecommerce
- Contexto: el diseño inicial contemplaba uuid para User y el paquete `com.bloom.api`; el proyecto ya usaba `com.blossom.ecommerce`.
- Decisión: todos los IDs `Long` con `GENERATED BY DEFAULT AS IDENTITY` (BaseEntity único); paquetes por feature bajo `com.blossom.ecommerce`.
- Consecuencia: el seed inserta IDs explícitos (OVERRIDING SYSTEM VALUE) y reinicia las secuencias en 100.

## D9 — Herencia JOINED y peso en gramos
- `Product` abstracta JOINED → `physical_products` (stock, `weight_grams` int) y `digital_products` (download_url, license_type PERSONAL/COMMERCIAL). `@Version` en Product contra sobreventa.
- `OrderItem.unit_price` congela el precio; Order↔Product es N↔N vía OrderItem.

## D10 — Credenciales demo (solo desarrollo, vienen en V2__seed.sql)
- Admin: `admin@bloom.test` / `Admin123!` · Cliente: `cliente@bloom.test` / `Cliente123!` (hash BCrypt coste 10).
- Deben eliminarse o cambiarse fuera de desarrollo.

## D11 — Refresh token opaco en BD con rotación (ajusta D4)
- Contexto: D4 dejaba la revocación inmediata como roadmap; se quiso logout real y detección de robo.
- Decisión: access token JWT HS256 (15 min, claims `sub`, `email`, `role`, sin consulta a BD por petición) + refresh token **opaco** (32 bytes aleatorios, base64url, 7 días). En BD (`refresh_tokens`, V3) solo el hash SHA-256 y un `family_id`. Cada `/auth/refresh` revoca el token usado y emite otro de la misma familia; si llega uno ya revocado se revoca toda la familia (replay/robo). `/auth/logout` revoca la familia y es idempotente (204). `findByTokenHash` con bloqueo pesimista para que dos refresh simultáneos no roten el mismo token.
- Descartada: refresh como JWT (no revocable sin lista) y token en claro en BD (una fuga de BD daría sesiones válidas).
- Consecuencia: el access token ya emitido sigue válido hasta expirar (máx. 15 min) tras el logout. Los tokens expirados no se purgan aún (limpieza programada = roadmap).

## D12 — Rate limit y bloqueo temporal en login
- Rate limit: ventana deslizante en memoria por IP (`getRemoteAddr`), **10 intentos / 60 s** → 429 con `Retry-After`. Config `app.security.login.rate-limit-*`.
- Bloqueo: **5 fallos consecutivos** bloquean la cuenta **15 min** → 423 con `Retry-After`; un login correcto pone el contador a 0; al expirar el bloqueo se limpia solo. Columnas `failed_login_attempts` y `locked_until` en `users` (V3). `login` usa `noRollbackFor` para que el contador persista aunque se lance la excepción.
- Correo inexistente y contraseña incorrecta devuelven el mismo 401 «Credenciales inválidas» y se compara contra un hash descartable para igualar tiempos (evita enumerar usuarios).
- Consecuencia/límite: el limiter en memoria vale para una instancia; con réplicas o proxy inverso habría que moverlo a Redis y configurar `forward-headers-strategy` para ver la IP real. El bloqueo por cuenta permite que un tercero bloquee a un usuario a propósito (trade-off aceptado, dura 15 min).

## D13 — Registro y roles
- `/auth/register` solo crea `CUSTOMER`; el admin es únicamente el del seed (D10). Correo normalizado (trim + minúsculas). Contraseña fuerte: 8–72 caracteres (tope de BCrypt) con mayúscula, minúscula, número y símbolo (`@StrongPassword`).
- Login/registro/refresh devuelven el mismo `AuthResponse` (tokens + `expiresIn` en segundos + usuario) para que el front no necesite otra llamada.
- Roles vía `@EnableMethodSecurity` + `@PreAuthorize("hasRole('ADMIN')")`; authority `ROLE_<role>`.

## D14 — Errores y capa web de seguridad
- `GlobalExceptionHandler` extiende `ResponseEntityExceptionHandler`: todo error (incluidos 404/405/415 de Spring MVC) sale como `ProblemDetail` `application/problem+json`; validación añade `errors` campo→mensaje. Sin esto el catch-all convertía los 404 en 500.
- 401/403 generados por los filtros de Spring Security (no pasan por `@RestControllerAdvice`) se escriben igual en ProblemDetail desde `ProblemDetailSecurityHandlers`.
- `JwtAuthenticationFilter` NO es `@Component` (se instancia en `SecurityConfig`) para que Boot no lo registre también como filtro del servlet. Token inválido → petición anónima → 401 por las reglas de acceso.
- Públicos: `/api/v1/auth/**`, `GET /api/v1/products/**` y `/categories/**`, swagger, `/v3/api-docs`, `/actuator/health`. CORS desde `app.cors.allowed-origins`, sin credenciales (bearer en cabecera), CSRF desactivado por ser stateless. El access token no va en cookie → no hay superficie CSRF; guardarlo en el front es el trade-off clásico (XSS) a mencionar en la entrevista.

## D15 — Catálogo y órdenes: decisiones de contrato
- Búsqueda: `ProductRepository` + `JpaSpecificationExecutor` (`ProductSpecifications.filter`): nombre (LIKE case-insensitive con `%` y `_` escapados), `categoryId`, `minPrice`/`maxPrice`, AND entre los presentes. Paginación `PageResponse` propia (no `Page` crudo) con tope `size ≤ 50` (defecto 12). Orden solo por `id,name,price,createdAt`: otra propiedad o `minPrice > maxPrice` → 400 (evita 500 por propiedad inexistente).
- Producto con herencia JOINED en un solo DTO: `ProductRequest.type` (PHYSICAL/DIGITAL) + campos opcionales validados en el servicio según el tipo; el tipo no se puede cambiar en un PUT (400). `downloadUrl` **no se expone** en el catálogo público: es lo que se vende.
- DELETE de producto: duro, pero 409 si figura en alguna orden (el historial manda). Alternativa descartada: borrado lógico (más columnas y filtros en cada consulta, sin requisito que lo pida).
- Referencias inválidas en el cuerpo (categoría o producto inexistente) → 400; recurso inexistente en la ruta → 404.
- `POST /orders`: líneas repetidas del mismo producto se suman; stock solo se controla en `PhysicalProduct` (digitales sin límite); `unitPrice` se congela y el total se calcula en la misma transacción. Cantidad 1–100 por línea, máx. 50 líneas.
- Órdenes ajenas responden **404**, no 403, para no revelar que existen. `/orders/**` es CUSTOMER; el admin no compra.
- `GET /orders/me` paginado y siempre `createdAt desc, id desc`; `default_batch_fetch_size=50` evita N+1 de ítems/productos sin romper la paginación (un fetch join paginaría en memoria).

## D16 — Inventario sin sobreventa: reintento ante bloqueo optimista
- Contexto: `@Version` en `Product` evita la venta doble, pero N compradores simultáneos hacían fallar a los perdedores con 409 aunque quedara stock.
- Decisión: `OptimisticRetry` (máx. 5 intentos) envuelve `OrderOperations.place`, que abre **una transacción nueva por intento** (por eso la transacción vive en otro bean: un `@Transactional` en el mismo método no se puede reintentar desde dentro). Al reintentar se relee el stock: si ya no alcanza, 409 «Stock insuficiente».
- Prueba: `OrderConcurrencyIntegrationTest` (hilos + Postgres real). Con `MAX_ATTEMPTS=1` falla con `ObjectOptimisticLockingFailureException`; con 5 pasa: se venden exactamente las unidades disponibles. Con ≤ 5 compradores simultáneos el reintento es determinista (cada ronda gana al menos uno); con más contención podría agotarse y devolver 409 (`ObjectOptimisticLockingFailureException` → ProblemDetail «Conflicto de concurrencia»).
- Descartada: `SELECT … FOR UPDATE` (serializa todo el producto) y `UPDATE … SET stock = stock - ? WHERE stock >= ?` (atómico y más simple, pero se pierde el uso de `@Version` que pide el modelo; es la alternativa a mencionar en la entrevista).

## D17 — Máquina de estados de la orden
- `PENDING → PAID → SHIPPED → DELIVERED`; cancelar solo desde `PENDING` o `PAID`; `DELIVERED` y `CANCELLED` son finales (`OrderStatus.canTransitionTo`). Transición inválida → 409.
- `POST /orders/{id}/cancel` (cliente dueño, solo `PENDING`) y `PATCH /orders/{id}/status` (ADMIN). No hay pasarela de pago: `PAID` lo marca el admin (simulación documentada).
- Cancelar **repone el stock** de los productos físicos en la misma transacción. `Hibernate.unproxy` porque `OrderItem.product` es un proxy perezoso de la clase abstracta y `instanceof PhysicalProduct` falla sobre el proxy.
- V4: `orders.version` (`@Version`) para que dos cambios simultáneos (cancelar dos veces, enviar y cancelar) no se pisen ni repongan stock dos veces; cubierto por test con hilos. Los cambios de estado usan el mismo reintento de D16.
- Descartada: permitir cancelar órdenes enviadas (implicaría devoluciones/reembolso, fuera de alcance).

## D18 — Evidencia de SQL: índices de búsqueda
- V5: GIN `pg_trgm` sobre `LOWER(name)` (el btree de V1 no sirve con `LIKE '%x%'`) y btree `(category_id, price)` en lugar de `category_id` solo.
- Medido con 200 000 productos (`EXPLAIN` sobre datos sintéticos): búsqueda por nombre ~55–68 ms → ~0.25 ms (`Seq Scan` → `Bitmap Index Scan`); los tres filtros ~12–37 ms → ~0.3 ms. La consulta solo por categoría+precio ya era rápida por el `LIMIT`; el compuesto quita filas descartadas.
- Coste asumido: el GIN encarece escrituras en `products`. La extensión `pg_trgm` se crea desde Flyway (es «trusted» desde PG13).

## D19 — Notificación de orden: puerto + adaptador simulado
- `OrderNotifier` (puerto) y `LogOrderNotifier` (adaptador que escribe en log con el correo enmascarado). `OrderOperations` publica un `OrderEvent` y `OrderNotificationListener` lo despacha `AFTER_COMMIT`: un intento revertido por concurrencia no notifica y un fallo del notificador no afecta la orden.
- Cambiar a correo real = otro adaptador (`@Component`) sin tocar el dominio. Sin cola ni reintento de envío (fuera de alcance).

## D20 — X-Request-Id y contrato OpenAPI fijado
- `RequestIdFilter` (orden máximo): usa el `X-Request-Id` del cliente solo si cumple `[A-Za-z0-9._-]{1,64}` (evita inyección en logs), si no genera UUID. Va al MDC (patrón `%X{requestId}` en cada línea), a la cabecera de respuesta y a `requestId` de **todo** ProblemDetail (`ResponseBodyAdvice` + handlers de seguridad). CORS lo permite y lo expone.
- Contrato: `docs/openapi.json` en el repo del api; `OpenApiContractTest` compara `/v3/api-docs` y falla si cambia sin regenerar (`./mvnw test -Dtest=OpenApiContractTest -Dopenapi.update=true`). Limitación: los errores 4xx no están descritos por endpoint (todos son ProblemDetail, ver D14).

## D21 — Decisiones del front
- Tokens: access JWT **solo en memoria** (Redux, no persiste) y refresh en `localStorage` para restaurar sesión al recargar (silent refresh al arrancar). Trade-off XSS ya descrito en D14: un XSS podría leer el refresh; se mitiga con CSP y sin `dangerouslySetInnerHTML`. Descartado: ambos en localStorage (expone el access) y ambos en memoria (pierde sesión al recargar).
- Carrito: Redux + `localStorage`, accesible sin login; el login se pide en el checkout (vuelve al carrito tras autenticarse). Los precios del carrito son referencia: el api congela el precio real al crear la orden.
- Admin: panel básico (CRUD de productos con `version` para evitar pisar cambios y cambio de estado de órdenes). El api no lista órdenes ajenas: se añade `GET /orders` (ADMIN, paginado) después y se regenera `docs/openapi.json`.
- Extras de front: skeletons, estados vacíos con ilustración y toasts; rutas con lazy loading y error boundary; accesibilidad AA verificada con axe en los tests. Modo oscuro y tema propio ya estaban en el plan de marca.

## D22 — Listado de órdenes para ADMIN
- `GET /orders` (solo ADMIN, paginado, `status` opcional, `createdAt desc, id desc`) cierra el hueco que dejó D15 (el admin cambiaba estados a ciegas). Su `@PreAuthorize` de método sustituye al de clase (CUSTOMER). `OrderResponse.customerEmail` identifica al cliente.
- Un ADMIN sigue sin poder ver el detalle `/orders/{id}` de otros (solo el dueño); el listado ya trae los ítems.
